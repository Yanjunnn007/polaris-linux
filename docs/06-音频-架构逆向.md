# polaris 扬声器（TAS2559）调研：根因定位与完整方案

> 生成日期：2026-10-13
> 方法：从**真 polaris dtb**（14 个变体）提取硬件参数 + 对照主线 beryllium（同 SoC 同功放）实现 + 逐行审读 `tas2559.c` 驱动
> 定位：**只做调研，不修改任何已有文件**。本文所有结论都给了可复查的出处。
>
> **⚠️ 本文推翻了 `扬声器攻坚与冻结诊断记录.md` 的核心判断**，见第 1 节。

---

## 0. 一句话结论

**之前找错了三样东西：芯片型号、GPIO、驱动。** 真 polaris 用的是 **TAS2559**（不是 tas2557）、复位脚是 **TLMM GPIO14**（不是 GPIO76）、而内核里 **`tas2559.c` 驱动和 `tas2559_uCDSP.bin` 固件一直都在**，`CONFIG_SND_SOC_TAS2559=m` 也已经开了。

**`-EIO` 的根因**：`tas2559.c` 是**双芯片驱动**（同时管理 TAS2559 + TAS2560），probe 时会向 `0x4c` **和** `0x4d` 两个地址都写数据（`DevBoth = DevA | DevB`），**且 DevB 的返回值会覆盖 DevA 的**。polaris 确实有两颗芯片（14 个变体 dtb 全部声明），所以问题不是"芯片不存在"，而是 **0x4d 那颗没被正确唤醒**——而它一旦不应答，**整个驱动 probe 都会失败，连 0x4c 也一起用不了**。

**抄谁的已经有了**：Poco F1（beryllium）在主线里已完整实现同样的 TAS2559 + TAS2560 组合，同 SDM845、同样 i2c5（SE5），**连 I2C 地址都完全相同（0x4c/0x4d）**，只有 reset GPIO 不同（polaris 是 14/25）。

**还有一个必须先验证的疑点**：vendor 的两份资料对外放走哪颗芯片说法不一致（见 1.7），实测 `playback.sh` 指向 **TAS2560**，而 `mixer_paths.xml` 完全没提 TAS——这会影响后续方案，所以第 0 步就要在实机确认。

---

## 1. ⚡ 对既有结论的修正（最重要的一节）

`扬声器攻坚与冻结诊断记录.md` 里记录的全部排查，都建立在**不是 polaris 的 dtb** 之上。

### 1.1 错在哪

那台机器的参数来源是 `~/bootx2/android.dts`。而该文件的 model 是 **`"Xiaomi Technologies, Inc. Equuleus P0 v2"`——Mi 8 Pro**，不是 polaris（这个错误在相机调研时已经确认过一次，见 `相机硬件参数实测.md` 发现一）。扬声器这条线当时没有跟着重查。

| 项 | 记录里写的 | **真 polaris dtb 实测** |
|---|---|---|
| 功放芯片 | ~~ti,tas2557~~ | **`ti,tas2559`** |
| 复位脚 | ~~`&tlmm 76 GPIO_ACTIVE_HIGH`~~ | **`&tlmm 14`**，flags = **0（ACTIVE_HIGH）** |
| 中断脚 | ~~`&tlmm 30`~~ | **`&tlmm 24`** |
| 驱动属性名 | ~~`ti,cdc-reset-gpio`~~ | **`ti,tas2559-reset-gpio`** |

### 1.2 为什么 tas2557 那条路注定失败

`tas2557.c:1625` 用的是 `devm_gpiod_get(dev, "ti,cdc-reset", ...)` —— 属性名是 **`ti,cdc-reset-gpio`**，而 polaris dtb 里写的是 **`ti,tas2559-reset-gpio`**。名字对不上 → 该属性根本不会被读取。

即使当时把属性名改对，装上去的也是**错芯片的驱动**（tas2557 vs tas2559 是两颗不同的芯片，寄存器映射不同）。

### 1.3 那个 `-EIO` 的真正原因

记录里把 `-EIO` 归因于"i2c5 的 QUP wrapper0 GPI DMA 路径故障"，并花了大量篇幅对比 i2c-14（触摸屏，走 wrapper1）。**这个方向是错的。**

真正原因在**驱动与硬件不匹配**。分两层：

**第一层：当时用的 `tas2557.c` 根本不读 polaris 的属性**

```c
/* tas2557.c:1625 */
pTAS2557->mnResetGPIO = devm_gpiod_get(dev, "ti,cdc-reset", GPIOD_OUT_LOW);
```

它找的是 `ti,cdc-reset-gpio`，而 polaris dtb 里写的是 `ti,tas2559-reset-gpio`。名字对不上，**复位脚全程没被驱动控制过**——芯片可能一直处在复位态，自然不应答。

**第二层：换用正确的 `tas2559.c` 后，会出现"双芯片"问题**

`tas2559.c` 是**同时管理 TAS2559 + TAS2560 的双芯片驱动**：

```c
/* tas2559.c:125-127 */
DevA = 0x01,
DevB = 0x02,
DevBoth = (DevA | DevB),        /* = 0x03 */

/* tas2559.c:2217 —— probe 第一件事就是向"两个设备"写 */
nResult = tas2559_dev_write(pTAS2559, DevBoth, TAS2559_SW_RESET_REG, 1);
```

而 `DevBoth` 会展开成**两次独立的 I2C 写**，且 **DevB 的结果会覆盖 DevA 的**：

```c
/* tas2559.c:422-428 */
if (chn & DevA)
	nResult = tas2559_i2c_write_device(..., pTAS2559->mnDevAAddr, ...);  /* 0x4c */
if (chn & DevB)
	nResult = tas2559_i2c_write_device(..., pTAS2559->mnDevBAddr, ...);  /* 0x4d ← 覆盖 */
```

**这里必须纠正本文初稿的一个错误判断**：我最初以为"polaris 只焊了一颗芯片、0x4d 不存在"。**这个推断是错的**，而且它还有个更糟的后果——`0x4d` 的失败恰恰说明**问题不在 tas2559（0x4c），而在 tas2560（0x4d）那颗芯片没起来**。

`NACK` 在 GPI DMA 模式下的报错形态：

```c
/* i2c-qcom-geni.c:522-531 */
static void i2c_gpi_cb_result(void *cb, const struct dmaengine_result *result)
{
	if (result->result != DMA_TRANS_NOERROR) {
		dev_err(gi2c->se.dev, "DMA txn failed:%d\n", result->result);
		gi2c->err = -EIO;
	}
}
```

**`DMA txn failed` = "目标地址没应答"，不是"DMA 引擎坏了"。** SDM845 的 QUP 硬件禁用了 FIFO（`FIFO_IF_DISABLE`），所有 I2C 传输都必须走 GPI DMA，所以**任何 NACK 都会以 "DMA txn failed" 的形式出现**——这正是当初误判的根源。

### 1.3.1 【更正】polaris 确实有两颗功放芯片

本文初稿（以及旧记录）都认为 polaris 只有一颗功放。**实测 14 个变体的 dtb，全部同时声明了 TAS2559 和 TAS2560**：

```
variant              2559rst 2559irq 2560rst 2560irq  2559addr 2560addr
--------------------------------------------------------------------------
Polaris_MP            14      24      25      30       0x4c     0x4d
Polaris_MP_V2         14      24      25      30       0x4c     0x4d
Polaris_MP_v2.1       14      24      25      30       0x4c     0x4d
Polaris_P0            8       24      25      30       0x4c     0x4d
Polaris_P1            8       24      25      30       0x4c     0x4d
Polaris_P2            14      24      25      30       0x4c     0x4d
Polaris_P3            14      24      25      30       0x4c     0x4d
（P0_v2 / P1_v2 / P1_v2.1 / P2_v2 / P2_v2.1 / P3_v2 / P3_v2.1 同上）
```

**两套 GPIO 完全独立**（2559 用 14/24，2560 用 25/30），这正是双芯片接线的特征——如果是单芯片，不会给不存在的芯片单独分配复位脚和中断脚。

**vendor 侧的铁证**（`vendor.img` @0x21c28e00 的 tinymix 脚本）：

```sh
function enable_speaker {
    tinymix 'Program' 2
    tinymix 'Configuration' 11
    tinymix 'TAS2559 DAC Playback Volume' 0      # ← 2559 静音
    tinymix 'TAS2560 DAC Playback Volume' 15     # ← 2560 出声
}
function enable_receiver {
    tinymix 'Program' 1
    tinymix 'TAS2559 DAC Playback Volume' 15     # ← 2559 出声（听筒）
    tinymix 'TAS2560 DAC Playback Volume' 0      # ← 2560 静音
}
```

**分工明确**：

| 场景 | TAS2559 (0x4c) | TAS2560 (0x4d) |
|---|---|---|
| **enable_speaker**（外放） | 静音（vol=0） | **出声（vol=15）** |
| **enable_receiver**（听筒） | **出声（vol=15）** | 静音（vol=0） |
| disable_*（都关） | 15 | 15 |

> **⚠️ 这条指向一个重要结论**：按 vendor 的测试脚本，**polaris 的外放扬声器走的是 TAS2560（0x4d）**，而 2559（0x4c）负责听筒。
>
> 但这与另一份 vendor 资料矛盾（见 1.7），**必须实机确认**。之所以要标红，是因为如果确实如此，`tas2559.c` 这个驱动的角色定位（以 TAS2559 为主体设计）会让 mainline 移植更复杂。

### 1.3.2 关于 "GPI DMA 失败" 的再解释

现有记录里的 `geni_i2c 894000.i2c: DMA txn failed:3` 和 `GPI transfer failed: -5`，**与本节结论并不矛盾，而是同一件事的两种表现**：NACK 由 DMA 回调上报（见 1.3 的代码）。`-5` = `-EIO`，正是回调里设的值。

**换句话说**：不是 DMA 有问题才导致 NACK，而是**目标地址没应答（NACK），而 NACK 只能通过 DMA 回调报出来**。

### 1.4 probe 的完整失败链条（已逐行核对）

```c
/* tas2559.c:2207-2219 */
if (pClient->dev.of_node)
	tas2559_parse_dt(&pClient->dev, pTAS2559);   /* ① 读 GPIO14/24/25/30 + addr 0x4c/0x4d */
tas2559_hw_reset(pTAS2559);                          /* ② 拉高 GPIO14（A）和 GPIO25（B）*/
nResult = tas2559_dev_write(pTAS2559, DevBoth, TAS2559_SW_RESET_REG, 1);
                                                     /* ③ 写 0x4c ? → 写 0x4d ✗ NACK */
if (nResult < 0) {
	dev_err(&pClient->dev, "I2c fail, %d\n", nResult);   /* ④ nResult 已被 B 的结果覆盖 */
	goto err;                                        /* ⑤ probe 返回失败 */
}
```

**关键点**：`nResult` 在 `:426-428` 处被 DevB 的结果**覆盖**，所以无论 `0x4c` 这边多正常，只要 `0x4d` 失败，整个 probe 就会判定失败。**日志里那条 `I2c fail` 因此掩盖了一个重要事实：失败的是 TAS2560，不是 TAS2559。**

### 1.5 那么 `0x4d` 为什么不应答？

这是**真正需要现场验证的环节**。可能原因（按可能性排序）：

| # | 假设 | 为什么可疑 | 怎么验 |
|---|---|---|---|
| 1 | **TAS2560 的复位脚没被拉起来** | `hw_reset()` 会拉高 GPIO25，但 polaris dtb 里**没有给 GPIO25 写 pinctrl 配置**（见 1.6） | 示波器/万用表量 GPIO25，或改 dts 补 pinctrl |
| 2 | **TAS2560 独立供电未开** | Android dtb 里 tas 节点没有任何 supply 属性（和记录里一致） | 查原理图 / 量 0x4d 的 VDD |
| 3 | **0x4d 那颗芯片在 MIX 2S 上没焊** | 但 14 个变体都声明了它，且 vendor 脚本真的在用它 → **可能性很低** | `i2cdetect` 扫 0x4d |
| 4 | 复位时序不够 | `hw_reset` 里每个脚只 `msleep(5)`+`msleep(2)` | 增加延时试 |

**注意第 3 条**：vendor 的 tinymix 脚本明确用 `TAS2560 DAC Playback Volume` 控制外放，**说明 0x4d 上确实有芯片**。所以问题更可能是 1/2/4 这类"芯片没被正确唤醒"。

### 1.6 关于 GPIO14 / GPIO25 的 pinctrl（已核实，不是问题）

真 polaris dtb 里确有 `cam_sensor_mclk1_*` 和 `cam_sensor_ir_*` 这些 pinmux 节点，字面上也覆盖 gpio14 / gpio25。但**逐条解析 phandle 后确认，它们都没有被任何相机节点实际引用**：

```
cam-sensor@0（主摄）  pinctrl-0 → cam_sensor_mclk0 (gpio13) + cam_sensor_rear
cam-sensor@1（副摄）  pinctrl-0 → cam_sensor_mclk3 (gpio16) + cam_sensor_rear2
cam-sensor@2（前摄）  pinctrl-0 → cam_sensor_mclk2 (gpio15) + cam_sensor_front
```

**MCLK1（gpio14）和 cam_sensor_ir（gpio25）是"定义了但没人用"的死节点**——典型的 Qualcomm 参考 dts 残留。

所以：**GPIO14/GPIO25 实际是空闲的**，`tas2559.c` 用 `devm_gpiod_get(..., GPIOD_OUT_LOW)` 请求它们不会有功能冲突。

> 这条**推翻了我自己的一个早期推测**：最初看到 `cam_sensor_mclk1 = gpio14` 就怀疑复位脚被相机占用，实际核对 phandle 后发现并非如此。**这正是"必须解析引用关系、不能只看名字"的例子。**
>
> 但它也留下一个**值得实机确认的小问题**：既然原厂 dtb 里没有 tas 的 pinctrl state，那 GPIO14/25 在开机后的驱动状态取决于 bootloader 给了什么。**如果实测发现 probe 仍失败，第一个该量的就是这两个脚的电平。**

### 1.7 ⚠️ 一个尚未解决的分歧：外放到底走哪颗芯片？

调研中发现**两份 vendor 资料互相矛盾**，必须现场验证，不能想当然：

**证据 A：`/vendor/bin/playback.sh`（测试脚本）**
```sh
function enable_speaker {          # $2 == 1
    tinymix 'Program' 2
    tinymix 'Configuration' 11
    tinymix 'TAS2559 DAC Playback Volume' 0      # 2559 静音
    tinymix 'TAS2560 DAC Playback Volume' 15     # 2560 出声
}
function enable_receiver {         # $2 == 2
    tinymix 'Program' 1
    tinymix 'TAS2559 DAC Playback Volume' 15     # 2559 出声
    tinymix 'TAS2560 DAC Playback Volume' 0
}
```
→ 按此脚本，**扬声器走 TAS2560**。

**证据 B：`/vendor/etc/mixer_paths.xml` 的 `<path name="speaker">`**
```xml
<path name="speaker">
    <ctl name="SLIM RX3 MUX" value="AIF1_PB" />
    <ctl name="RX1 MIX1 INP1" value="RX3" />
    <ctl name="CLASS_H_DSM MUX" value="DSM_HPHL_RX1" />
    <ctl name="HPHL DAC Switch" value="1" />
    <ctl name="COMP1 Switch" value="1" />
</path>
```
→ 全是 **WCD9340 内部 codec** 的控件（CLASS_H / HPHL / COMP1），**完全没提 tas 芯片**。

**怎么解释这个矛盾**：`mixer_paths.xml` 很可能来自 Qualcomm 参考设计（CDP/MTP），高通参考板用的是 WCD9340 的 class-H 功放直接推喇叭；小米换了 TAS 方案后**没有同步改这个 XML**，而是把真正的扬声器控制放在 `playback.sh` / 音频 HAL 里。

**结论**：**以 `playback.sh` 为准**（它是设备实测脚本）。但这意味着——

> **⚠️ polaris 的外放扬声器很可能接在 TAS2560（0x4d）上，而不是 TAS2559（0x4c）。**
>
> 而 `tas2559.c` 这个驱动的 DAI 名与寄存器映射是**围绕 TAS2559（DevA）设计的**，TAS2560（DevB）只是"辅助"角色。**"扬声器走 2560"这件事会让 mainline 移植明显更复杂**（可能要改驱动，或者只能在 dts 里把两颗都配上，看 DAC 音量控件能否分别控制）。

**这一条必须在实机上验证**（见 5.1 第 0 步），不能靠推理定论。

**换句话说**：不是 DMA 有问题才导致 NACK，而是**目标地址不存在导致 NACK，而 NACK 只能通过 DMA 回调报出来**。

## 2. 硬件事实（真 polaris dtb 实测）

来源：`backups/parts/boot.img` 提取的 14 个 polaris dtb，纯 Python FDT 解析器解码。

### 2.1 全部 14 个变体的一致性

```
Polaris_MP / MP_V2 / MP_v2.1 / P2 / P2_v2 / P2_v2.1 / P3 / P3_v2 / P3_v2.1
    →  reset = GPIO14, irq = GPIO24
Polaris_P0 / P0_v2 / P1 / P1_v2 / P1_v2.1
    →  reset = GPIO8,  irq = GPIO24
```

**只有复位脚有差异**（P0/P1 早期样机用 GPIO8，量产 P2/P3/MP 用 GPIO14），其余完全一致。
**MIX 2S 量产机应该按 GPIO14 走**（MP = Mass Production）。

### 2.2 完整节点

```dts
/* 真 polaris dtb: /soc/i2c@894000/tas2559@4c */
compatible = "ti,tas2559";
reg = <0x4c>;
status = "ok";

ti,bit-rate      = <0x10>;      /* 16-bit I2S */
ti,echo-ref      = <0x00>;
ti,tas2559-addr  = <0x4c>;
ti,tas2559-channel = <0x00>;
ti,tas2559-reset-gpio = <&tlmm 14 0>;   /* flags=0 → ACTIVE_HIGH */
ti,tas2559-irq-gpio   = <&tlmm 24 0>;

/* 以下 4 条是"双芯片"配置的残留，polaris 上不成立 */
ti,tas2560-addr        = <0x4d>;
ti,tas2560-channel     = <0x01>;
ti,tas2560-irq-gpio    = <&tlmm 30 0>;
ti,tas2560-reset-gpio  = <&tlmm 25 0>;

ti,ycrc-enable = <0x01>;
```

### 2.3 I2C 总线

```
/soc/i2c@894000
  compatible = "qcom,i2c-geni"
  reg = <0x894000 0x4000>          ← SE5, QUP wrapper0
  qcom,wrapper-core = <&gpi_dma0>  （phandle 0x40 → qupv3_0_geni_se@8c0000）
  dmas = <&gpi_dma0 0 5 QCOM_GPI_I2C>,
         <&gpi_dma0 1 5 QCOM_GPI_I2C>
  dma-names = "tx", "rx"
  clock-frequency 未在 dts 里声明 → 默认 100kHz（标准模式）
  pinctrl: gpio85(SCL) / gpio86(SDA)，function "qup5"
```

### 2.4 音频通路（真 polaris dtb）

```
/soc/qcom,msm-audio-apr/sound-tavil
  compatible = "qcom,sdm845-asoc-snd-tavil"
  qcom,model = "sdm845-tavil-snd-card"
  qcom,wsa-max-devs = <0>            ← WSA881x 功放未启用
  asoc-codec = <&msm-stub-codec &msm-ext-disp-audio-codec-rx>
                 (phandle 0x31c / 0x31d)

/soc/slim@171c0000/tavil_codec
  compatible = "qcom,tavil-slim-pgd"   ← WCD9340 耳机 codec
  swr_master/wsa881x@... × 4           ← 节点存在但 max-devs=0，不用
```

**结论**：外放**走 TAS2559 + TAS2560 这对芯片**，通过 `QUATERNARY_MI2S_RX` 喂数据；WSA881x 那条路 polaris 没用（`qcom,wsa-max-devs = 0`）。至于"具体哪颗芯片负责外放"，见 1.7 的存疑说明。

## 3. 现成可抄的答案：beryllium（Poco F1）

**这是本次调研最有价值的发现**——同一个 SoC、同一颗功放芯片、同样的 i2c5，主线里已经跑通了。

### 3.1 beryllium 的完整实现（`sdm845-xiaomi-beryllium-common.dtsi`）

```dts
/* 第 478-496 行 */
&i2c5 {
	#dma-cells = <3>;
	status = "okay";
	dmas = <&gpi_dma0 0 5 QCOM_GPI_I2C>,
	       <&gpi_dma0 1 5 QCOM_GPI_I2C>;
	dma-names = "tx", "rx";

	/*smart PA*/
	tas2559_codec: tas2559@4c {
		#sound-dai-cells = <1>;
		compatible = "ti,tas2559";
		reg = <0x4c>;
		ti,tas2559-reset-gpio = <&tlmm 12 0>;
		ti,tas2560-reset-gpio = <&tlmm 76 0>;
		ti,tas2559-addr = <0x4c>;
		ti,tas2560-addr = <0x4d>;
	};
};

/* 第 575-581 行：QUAT MI2S 用 1 条 SD line */
&q6afedai {
	dai@22 {
		reg = <QUATERNARY_MI2S_RX>;
		qcom,sd-lines = <0>;
	};
};

/* 第 638-698 行：声卡 */
&sound {
	compatible = "qcom,db845c-sndcard", "qcom,sdm845-sndcard";
	pinctrl-0 = <&quat_mi2s_active &quat_mi2s_sd0_active>;
```

## 4. 需要解决的关键问题

### 4.1 驱动的双芯片硬性要求（已确认不阻塞）

**驱动写死了双芯片**（`tas2559.c:1876-1884`）：

```c
pTAS2559->mnDevBGPIORST = devm_gpiod_get(dev, "ti,tas2560-reset", GPIOD_OUT_LOW);
if (IS_ERR(pTAS2559->mnDevBGPIORST)) {
	ret = PTR_ERR(pTAS2559->mnDevBGPIORST);
	dev_err(dev, "Failed to request reset gpio, error %d\n", ret);
	return ret;                     /* ← 非 optional，缺了就 probe 失败 */
}
```

`ti,tas2559-addr` / `ti,tas2560-addr` **两个也都是必需属性**（`of_property_read_u32` 失败直接 `-EINVAL`）。

**好消息**：polaris 的 4 个属性（2 个 reset GPIO + 2 个 addr）**在真 polaris dtb 里全都有**（见 1.3.1），所以**不需要用 dummy 值糊弄**——照抄即可：

| 属性 | polaris 真值 |
|---|---|
| `ti,tas2559-reset-gpio` | `<&tlmm 14 0>` |
| `ti,tas2560-reset-gpio` | `<&tlmm 25 0>` |
| `ti,tas2559-irq-gpio` | `<&tlmm 24 0>` |
| `ti,tas2560-irq-gpio` | `<&tlmm 30 0>` |
| `ti,tas2559-addr` | `<0x4c>` |
| `ti,tas2560-addr` | `<0x4d>` |

**所以 4.1 不是阻塞点**，真正要解决的是 **1.5 里那个"0x4d 为什么不应答"**。

> 特别注意：`tas2559.c` 在 probe 时**第一件事就是 `DevBoth` 写**，所以只要 0x4d 不应答，**整个驱动的 probe 都会失败，连 0x4c 也一起用不了**。这就是为什么"只修 0x4c 没用"——它们绑在一起。

### 4.2 固件：已经有了

```c
/* tas2559.h:293 */
#define TAS2559_FW_NAME "tas2559_uCDSP.bin"
/* tas2559.c:2235 */
nResult = request_firmware_nowait(THIS_MODULE, 1, TAS2559_FW_NAME, ...);
```

好消息：**`tas2559_uCDSP.bin` 已经在 polaris 的固件包里**：

```

    ./lib/firmware/tas2559_uCDSP.bin        ← 第 1 行就是它
device/community/firmware-xiaomi-beryllium/firmware.files:1
    /usr/lib/firmware/tas2559_uCDSP.bin
```

注意用的是 `request_firmware_nowait`（异步），**固件缺失不会阻塞 probe**，只会导致后面 DSP 配置失败。但既然文件已经在，这条不是问题。

### 4.3 内核配置：已经开了

```
    CONFIG_SND_SOC_TAS2559=m      ← 正是需要的那个
    CONFIG_SND_SOC_TAS2557=m      ← 这个是之前用错的
```

`tas2559.c` 的 of_match 表和 i2c_id：

```c
	{},

```

**驱动 → 配置 → 固件 三样都齐，唯一的问题是 dts 里没写。**

### 4.4 i2c5 的 GPI DMA 是否真的有问题？

**基于本次调研，没有证据表明有。**理由：

1. 主线 `sdm845.dtsi:1596-1616` 里 i2c5 的 dmas 是**默认就有的**，beryllium 只是重复声明了一遍（内容完全相同）。
2. beryllium 在**同一个 i2c5、同一个 GPI DMA 引擎**上，TAS2559 是能工作的（主线已合入多时）。
3. 记录里"i2c-14 正常、i2c5 异常"的对比，实际差异在于 **i2c-14 上挂的触摸屏会 ACK，i2c5 上的 0x4d 不会 ACK**。

**结论：先按"i2c5 是好的"来做。** 如果修好 dts 后仍然 `-EIO`，那时再查 DMA 不迟——但那时的现象会不同（应该能看到 0x4c 的 ACK 成功）。

### 4.5 声卡 `&sound` 节点

polaris 主线 dts 里**完全没有 `&sound` 覆盖**，而 `sdm845.dtsi:5636` 里只有空骨架：

```dts
sound: sound {
};
```

必须按 beryllium 的写法把 `&sound` 补全（compatible / pinctrl / model / audio-routing / dai-links）。

**注意一个细节**：`quat_mi2s_active`、`quat_mi2s_sd0_active` 这两个 pinctrl **已经在 `sdm845.dtsi:3369/3384` 里定义好了**，直接用即可，不需要自己写。

## 5. 建议的实施顺序

> 以下是**调研结论**，不是已经执行的操作。

**第 0 步（最重要，先做）：在不装驱动的前提下确认 i2c5 上两颗芯片都在**

```sh
# 找到 i2c5 在系统里的编号（可能是 i2c-5，也可能被重排）
i2cdetect -l | grep -i 894000

# ⚠️ 注意：geni-i2c 的 functionality 里屏蔽了 QUICK 模式
#    （i2c-qcom-geni.c:940: I2C_FUNC_I2C | (I2C_FUNC_SMBUS_EMUL & ~I2C_FUNC_SMBUS_QUICK)）
#    所以裸 i2cdetect -y 5 不可用，必须用读写方式探测：
i2cdetect -y -r 5        # read 模式（发 SMBus read byte）
# 或直接手动读寄存器
i2cget -y 5 0x4c 0x00    # TAS2559 的 page 寄存器
i2cget -y 5 0x4d 0x00    # TAS2560
```

**这一步能直接回答 1.5 的核心疑问**：
- 两颗都有应答 → 硬件通路 OK，问题在驱动/dts
- 只有 0x4c 应答 → 2560 没起来，去查 GPIO25 / 供电（1.5 的假设 1/2/4）
- 都不应答 → 复位脚 pinctrl 问题（1.6 的假设）优先

**第 1 步：补 dts**（两块）

```dts
&i2c5 {
	clock-frequency = <100000>;      /* polaris 原厂未声明，用保守值 */
	status = "okay";

	tas2559_codec: tas2559@4c {
		#sound-dai-cells = <1>;
		compatible = "ti,tas2559";
		reg = <0x4c>;
		ti,tas2559-reset-gpio = <&tlmm 14 0>;
		ti,tas2560-reset-gpio = <&tlmm 25 0>;
		ti,tas2559-addr = <0x4c>;
		ti,tas2560-addr = <0x4d>;
	};
};
```
`&sound` 照 beryllium 写，`model` 改成 `"Xiaomi Mi MIX 2S"`。

**第 2 步：重新构建 + 刷入**（流程见 `扬声器攻坚与冻结诊断记录.md` 第九节，已验证可行）

**第 3 步：验证**

```sh
dmesg | grep -iE "tas|i2c.*894000"     # probe 成功？有无 "I2c fail"
aplay -l                                # 应出现 "Primary Spkr Playback"
amixer -c 0 controls | grep -i tas       # 应看到 TAS2559/2560 DAC Playback Volume
# 参照 vendor 的做法分别点两颗芯片，确认哪颗推外放：

speaker-test -t sine -c 2
# 再换成 2559=0, 2560=15 试
```
**第 3 步的两次对比，就是在回答 1.7 那个存疑点。**

## 6. 为什么之前会走偏（复盘）

| 环节 | 问题 |
|---|---|
| **参数来源** | 用了 Equuleus（Mi 8 Pro）的 dtb，且没在该文件出错后重新核对音频部分 |
| **芯片型号** | 记录里还特意标注"不是 tas2559，某 AI 说是 tas2559 是错的"——**这条更正本身是错的** |
| **错误归因** | `-EIO` 被归因到 GPI DMA 硬件路径（一个很难查且当时无法证伪的方向），而没先确认"目标地址是否存在" |
| **缺少横向参考** | 没查 beryllium——**同 SoC 同芯片且主线已实现**，这是最该第一时间查的 |

**教训**：`-EIO` / NACK 类错误，第一件事应该是**确认从设备是否真的在那个地址上**，而不是先怀疑总线控制器。
