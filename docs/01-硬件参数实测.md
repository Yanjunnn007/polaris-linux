# polaris 相机硬件参数实测（从原厂 dtb 提取）

> 生成日期：2026-10-11
> 方法：从 `backups/parts/boot.img` 中提取 **真正的 polaris dtb**（14 个变体），用自写纯 Python FDT 解析器解码
> 本文只做调研，未改动任何文件

---

## 0. 本次调研的三个关键发现

### 发现一：之前查的 `android.dts` 不是 polaris 的

`~/bootx2/android.dts`（26082 行）的 model 是 **"Xiaomi Technologies, Inc. Equuleus P0 v2"**——那是 **Mi 8 Pro**，不是 MIX 2S。**这正是之前 GPIO8 检测 VBUS 走错路的根本原因**：参数来自另一台机器的 dtb。

### 发现二：boot.img 里有 65 个 dtb，其中 14 个是真正的 polaris

```
boot.img (67MB) → 65 个 FDT → 14 个 Polaris + 若干 Dipper/Equuleus/Ursa
```

已提取到 `C:\pmos\` 的 Polaris 变体：`Polaris_P0/P1/P2/P3/MP` 各代的 `v2` / `v2.1`。

**重要**：14 个 polaris 变体的相机参数**完全一致**（只有最早的 P0 的 VIO 供电不同），所以下面的参数可直接用。

### 发现三：传感器型号已实锤（从 vendor.img 挖出）

从 ROM 的 `vendor.img`（628MB）里搜到的**真实配置**：

| 摄像头 | 传感器 | 模组名（vendor 里的字符串） |
|---|---|---|
| **后置主摄** | **索尼 IMX363** | `polaris_...` / `semco_imx363` |
| **后置副摄** | **三星 S5K3M3** | `semco_s5k3m3` |
| **前置** | **OV5675** | `polaris_ov5675_primax` |

关键证据字符串：
```
com.qti.sensor.imx363.so          ← 主摄传感器驱动
com.qti.sensor.s5k3m3.so          ← 副摄传感器驱动
com.qti.sensor.ov5675.so          ← 前摄传感器驱动
com.qti.tuned.semco_imx363.bin    ← 主摄 tuning 数据（三星电机模组）
com.qti.tuned.semco_s5k3m3.bin    ← 副摄 tuning 数据
com.qti.tuned.primax_ov5675.bin   ← 前摄 tuning 数据
polaris_ov5675_primax             ← 明确带 polaris 前缀
```

**重要修正**：vendor.img 里**同时**存在 `dipper_imx363_semco` 和 `polaris_*` 的条目——因为小米把这些机型的配置打包在同一镜像里。**polaris 自己用的是 `polaris_ov5675_primax`**，说明确实是 polaris 的配置，不是 dipper 的。

**这也修正了之前的一个推测**：前摄是 **OV5675**（不是 S5K3T1，也不是 OV7251——那些是 beryllium/Poco F1 或 dipper 的）。

### 附：polaris 的相机 XML 配置（存在于 vendor.img）

```
vendor/lib/camera/components/etc/morpho_lowlight4.0.xml  ← 低光增强配置，含 <device name="polaris">
```

该 XML 明确写着 `<device name="polaris">`，内含按 ISO 分档的降噪参数（`ynr_weights`、`cnr_weights`、`obc`、`gamma` 等）——**这是做 libcamera tuning 时可参考的宝贵数据**。

### 发现四：三个传感器的驱动可用性不同 ⚠️

我核对了 `origin/sdm845/7.1-dev` 分支的 `drivers/media/i2c/`：

| 传感器 | 主线驱动 | 影响 |
|---|---|---|
| **IMX363**（主摄） | ✅ `imx363.c` 有 | **可以开工** |
| **OV5675**（前摄） | ✅ `ov5675.c` 有 | 以后可用 |
| **S5K3M3**（副摄） | ❌ **没有** | 只有 `s5k3m5.c`（是另一颗传感器，**不通用**） |

**结论**：**主摄（IMX363）是唯一现在就能做的**，也是最有价值的那颗。副摄 S5K3M3 需要自己写驱动（或找社区是否有 `s5k3m3.c`——本地 fork 里没有），属于另一个量级的工作。

**这正好和"先出图"的目标吻合**：主摄通 = 目标达成，不用等副摄。

## 1. polaris 三路摄像头（已确认）

从 `Polaris_MP_v2.1.dtb`（各变体一致）：

| 摄像头 | csiphy | cci master | MCLK | reset GPIO | VANA EN GPIO | 备注 |
|---|---|---|---|---|---|---|
| **后置主摄** (sensor@0) | **csiphy0** | 0 | **MCLK0** (pin 13) | **GPIO 80** | GPIO 87 | 另有 CAM_CUSTOM0 = GPIO 102 |
| **后置副摄** (sensor@1) | csiphy1 | 1 | **MCLK3** (pin 16) | **GPIO 28** | GPIO 79 | |
| **前置** (sensor@2) | csiphy2 | 1 | **MCLK2** (pin 15) | **GPIO 9** | GPIO 29 | |

**注意**：主摄用的是 **MCLK0 = GPIO 13**，不是别处常见的其他编号。

### 三路供电 rail（主摄）

| 供电 | 来源节点 | 实际是什么 |
|---|---|---|
| `cam_vana` = 2.96V | `/soc/rpmh-regulator-bobb1/regulator-bob` | PM8998 的 **BOB** 升压（2.8–3.6V 可调） |
| `cam_vdig` = 1.05V | `/soc/gpio-regulator@2`（名为 `camera_rear_ldo`） | **PM8998 GPIO 11** 使能，vin = SMPS3 |
| `cam_vio` = 1.8V | `/soc/gpio-regulator@6`（名为 `camera_vio_ldo`） | **TLMM GPIO 21** 使能，vin = PM8998 S4 |

### 全部 7 个相机供电 regulator（原厂定义）

| 节点 | 名称 | 电压 | 使能脚 | vin |
|---|---|---|---|---|
| gpio-regulator@0 | `actuator_rear_regulator` | 2.8V | TLMM 26 | BOB |
| gpio-regulator@1 | `actuator_rear_aux_regulator` | 2.8V | TLMM 27 | BOB |
| **gpio-regulator@2** | `camera_rear_ldo`（主摄 DVDD） | **1.05V** | **PM8998 GPIO 11** | SMPS3 |
| gpio-regulator@3 | `camera_ldo`（前摄 DVDD） | 1.05V | PM8998 GPIO 9 | PM8998 S4 |
| gpio-regulator@4 | `camera_aux_ldo`（副摄 DVDD） | 1.00V | TLMM 77 | SMPS3 |
| gpio-regulator@5 | `camera_ois_regulator` | 2.8V | TLMM 50 | BOB |
| **gpio-regulator@6** | `camera_vio_ldo`（共用 VIO） | **1.8V** | **TLMM 21** | PM8998 S4 |

### I2C / 附属器件

| 器件 | cci | slave-addr |
|---|---|---|
| `eeprom@0`（主摄 EEPROM） | 0 | **0xA0**（7-bit 0x50） |
| `eeprom@1`（副摄 EEPROM） | 1 | 0xA0 |
| `eeprom@2`（前摄 EEPROM） | 1 | **0x6C**（7-bit 0x36） |

## 2. 关于 PHY 类型（C-PHY vs D-PHY）—— 本次调研的边界

**结论：查了两轮，仍未能从静态文件确凿判定。这是一个"运行时决定"的参数。**

### 已排除的证据

**① 14 个 polaris dtb 里没有：**
| 关键词 | 结果 |
|---|---|
| `cphy` | 只出现在时钟名 `cphy_rx_clk_src` / `ife_cphy_rx_clk`（CSID 侧通用时钟名，**不表示走 C-PHY**） |
| `dphy` | 只出现在 USB 的 `qcom,usb-pdphy@1700`、`vdd-pdphy-supply`（**USB PD PHY，与相机无关**） |
| `bus-type` / `lane` 数 | **完全没有** |

**② vendor.img 里的 sensor module 配置也不是文本**：
高通的 `com.qti.sensormodule.imx363.bin` 是**二进制结构体**（camx 私有格式），不是 XML。我在 vendor.img 里成功定位到了它的字段表（`laneAssign` / `isComboMode` / `maxRollDegree` / `maxPitchDegree` / `maxYawDegree` / `pdafName` 等字段名连续排列），也找到了 `imx363` 名称字符串附近的结构体数据区，**但字段的具体取值需要 camx 的完整结构体定义才能正确解读**（每个字段是变长的 descriptor 数组）。

**③ 但有一条关键线索**：camx 的调试日志里有这么一句（存在于 vendor.img 的字符串表）：
```
[ VERB]%s %s:3067 %s() is3Phase %d, laneType %d laneNum 0x%x laneAssign 0x%x
```
`is3Phase`（是否三相位 = C-PHY）**是运行时从 sensor module 配置里读出来的变量**——所以它既可能为 0（D-PHY）也可能为 1（C-PHY），静态文件里查不到具体值。**这证明设备的相机栈两种都支持，实际用哪种由配置决定。**

### 为什么这**不阻塞**开工

**你们的 7.1-dev 内核两种模式都支持**（C-PHY 支持已在 fork 里，见另一份文档）。所以：

1. **先按 D-PHY 试**（和同 SoC 同传感器的 Poco F1 一致，其 dts 无 `bus-type` 即默认 D-PHY）；
2. 如果 CSIPHY 报 lane 配置错误 / 收不到数据，**改成 `bus-type = <MEDIA_BUS_TYPE_CSI2_CPHY>` 再试**；
3. 两种写法在 dts 里只差一行。

**这是"试错成本极低"的未知项**，不需要提前解决。

### 真想知道确凿答案的两条路（可选）

1. **在有 root 的 Android 设备上抓 camx 日志**：开启 verbose 后能看到 `is3Phase` 的实际值。但你们的手机已刷 pmOS，需先刷回 MIUI——成本高，不建议。
2. **反查 sensor module 结构体定义**：在 `git.codelinaro.org` 或高通开源仓里找 camx 的 `sensorModuleData` 结构体定义，按字节解码那段数据。属于"能做但性价比低"。

**建议**：直接试。D-PHY 不通就切 C-PHY，半小时能验完，比静态分析快得多。

## 3. 现有参数 vs 主线需要的写法（对照）

主线需要的是 `imx363` 驱动的标准 bindings：`vana` / `vdig` / `vif`（三路，非 optional）。

| 主线属性 | polaris 实际硬件 | 说明 |
|---|---|---|
| `vana-supply` | BOB (2.96V) | 对应 vendor 的 `cam_vana` |
| `vdig-supply` | PM8998 GPIO11 使能的 1.05V LDO | 对应 `camera_rear_ldo` |
| `vif-supply` | TLMM GPIO21 使能的 1.8V LDO | 对应 `camera_vio_ldo`（注意：主线 IMX363 叫 `vif` 而非 `vio`） |
| `reset-gpios` | **TLMM GPIO 80** | vendor 里 flag=0（ACTIVE_HIGH）⚠️ 见下 |
| `clocks` | **CAM_CC_MCLK0_CLK** | vendor 里 pin 13 的 `cam_mclk` |
| `clock-frequency` | **24000000**（24MHz） | vendor 里 `clock-rates = 0x16e3600` |

### ⚠️ 复位极性要实测

vendor dtb 里主摄 reset 的 `gpio-req-tbl-flags = 0x00000001`（对 MCLK），而 `gpios` 数组里 reset 项 flag 是 **0x0**。高通的 `gpio-reset` 语义和主线不同（高通是"拉低复位"还是"拉高复位"取决于驱动内部逻辑）。

**建议**：先按 `GPIO_ACTIVE_HIGH` 试，不通就换 `GPIO_ACTIVE_LOW`。这是 tas2557 那次踩过的同类坑。
